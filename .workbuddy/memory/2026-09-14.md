## 完成跨包事件总线基础设施

基于 pnpm workspace 公共子包（packages/shared）共享 EventEmitter 实例与事件类型，AI 引擎层通过 emit 发送任务状态事件，后端用 @OnEvent 监听。

### 关键设计决策
- **不用双实例**：shared 包不持有自己的 EventEmitter2 实例，避免与 NestJS EventEmitterModule 创建的实例形成"双实例"——否则 ai-engine emit 与 backend @OnEvent 不在同一实例上，事件收不到。
- **函数式 holder 方案**：shared 导出 `setEventBus(emitter)` + `emit(event, ...args)` 函数。backend 在 main.ts bootstrap 时调 `setEventBus(app.get(EventEmitter2))` 注入 NestJS 实例；ai-engine 调 `emit(...)` 转发到该实例。
- **零运行时依赖**：shared 只用结构化类型 `EventBusLike`（EventEmitter2 的子集），不 import eventemitter2，避免跨包版本冲突。
- **wildcard 模式**：EventEmitterModule.forRoot({ wildcard: true, delimiter: '.', global: true, maxListeners: 50 })，支持 @OnEvent('task.*') 通配。

### 修复：全局响应拦截器破坏 SSE（本次最关键的坑）
`TransformInterceptor` 会把**每条 SSE 消息**再包成 `{code,message,data}`，前端解析出的是嵌套结构 `data: {"data":"{...}"}` 而全部丢弃。

## 运维：前端 dev server OOM —— 根因是 `.next` 缓存膨胀（约 19:30）
- 现象：`next dev --turbopack` **两次**崩溃，且**几乎完全空闲**（第二次 1h37m 全程只服务了 1 个页面请求）。
  第一次堆涨到 11.3GB（默认上限），第二次给了 6GB 仍涨满到 5.7GB 被 OOM。
  约 1GB / 17min 的空闲涨堆速度 ⇒ 是**内存泄漏 / 缓存失控**，不是正常累积、更不是代码缺陷。
- **根因定位**：`apps/frontend/.next` 体积 **2.8GB / 25887 个文件**，其中 `.next/dev/cache` 单独占 **2.0GB**。
  Turbopack dev 会把持久化缓存读进内存，缓存膨胀后 dev server 空闲也会持续涨堆。
  （日志里早前那些 `MODULE_UNPARSABLE next/document.js`、`module factory is not available` 陈旧缓存告警是同一根源的征兆。）
- **修复**：`rm -rf apps/frontend/.next` + 重启 → 新 `.next` 仅 **122MB**（差 23 倍），dev server 正常。
  结论：**调大 `--max-old-space-size` 只是拖延，清缓存才是解法。**
- **启动方式**：`NODE_OPTIONS="--max-old-space-size=6144" COREPACK_ENABLE_DOWNLOAD_PROMPT=0 pnpm dev:frontend`，
  并套一层 `for i in 1..5; do ...; sleep 3; done` 自动重启兜底，避免测到一半页面死掉。

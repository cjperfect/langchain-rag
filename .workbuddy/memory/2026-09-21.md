# 2026-09-21 工作日志

## 答疑：RAG 是否一般以 tool 形式放在 agent 里

用户提问 RAG 与 agent 的常见组合方式。读了项目代码后给出结论（未改代码，纯分析）。

### 结论
- **不一定**。两种主流形态：
  - **A 固定前置检索**（经典 RAG）：检索无条件在生成前执行，模型无选择权。一次 LLM 调用，更快更省更可预测。适合「每个问题都要查文档」的纯知识库问答。
  - **B 检索作为 tool**（agentic RAG）：由 LLM 决定是否调、调几次。多一次往返，更灵活也更贵更慢。适合混合意图 / 多数据源 / 需改写重试的多跳。
  - 判断标准只有一条：**检索是否每次都需要**。是 → 做成 tool 是白付一次 LLM 往返。
  - 另有两变体：**意图路由**（前置廉价分类，闲聊绕开检索）、**每轮强制注入**。
- 做成 tool 是 agent 框架里的惯用做法（`createRetrieverTool` / `QueryEngineTool` / OpenAI `file_search`），但「惯用」≠「总是」。

### 本项目核实结果（重要）
- **本项目是 A+B 混合，不是纯 B**。`chat.service.ts:186 buildRagContext()` 做预检索（用户原话、k=5）注入 `<documents>`；agent 同时挂 `search_knowledge_base` 兜底。`prompts/system.ts:3-5` 的「知识来源（按优先级）」正是这个契约。
- **本项目用 B 的正当理由**：不是为了「决定要不要检索」（用户基本都在问文档，这个决定不值钱），而是为了**「检索不准时改写 query 重试」**（prompt 规定最多 2 次）——这个能力预检索给不了。
- 预检索用的是**未改写的用户原话**，质量不如工具改写版：有意的延迟/质量取舍。

### 发现的隐患（写入 MEMORY.md，未修）
- `tools/knowledge-search.ts:8` 的 `let lastSearchResults` 是**进程级共享可变状态**，`agent/index.ts:102` 在 `on_tool_end` 读它给前端展示知识来源 ⇒ **两会话并发时 A 可能读到 B 的检索结果，前端显示错误来源**。本机单人测试碰不到。
- 建议修法：`responseFormat: "content_and_artifact"` + 读 `event.data.artifact`（已用 node 核实 `@langchain/core@1.2.3` 类型里有这两个）。

### 补充：澄清「做成 tool 就是 agentic RAG 吗」（同一轮追问）
- **不是**。两个正交维度：**打包形式**（tool / graph 节点 / 中间件）与**控制权归属**（程序写死 vs 模型运行时决定）。agentic 与否由后者决定，前者只是接口形式。
  - tool 但不 agentic：只有一个工具 + prompt 强制必调 + 代码固定传用户原话 ⇒ 换了外壳的固定流水线。
  - 非 tool 但 agentic：LangGraph 节点 + 模型控边（Self-RAG / CRAG）。
- agentic 是**程度**而非布尔值，本项目自评：
  - **L0 固定流水线** ← 预检索主路径（`buildRagContext`）
  - **L2 模型决定 query 与次数** ← 兜底工具（改写重试最多 2 次）
  - L1（模型决定是否检索）、L3（模型评估结果后迭代）均未做。
- ⚠️ **实际推论**：若预检索每次都命中并注入 `<documents>`，模型就无需调工具 ⇒ **多数请求实际停在 L0**，agentic 只在兜底分支被激活。故「本项目是 agentic RAG」的说法不完全成立，这是延迟/质量的取舍而非缺陷。
- 术语提醒：「agentic RAG」无严格定义，2024 年前后流行的模糊词。判断一律用「控制权在谁手里」，不要被标签绑架。

### 定论：本项目是 agentic RAG 吗（用户直接追问）
核实结论：**不是整体的 agentic RAG，是「预检索为主的混合体，带一条真 agentic 的兜底分支」**。
- 佐证「有 agentic 成分」：`agent/index.ts:15` 无任何强制调用（无 tool_choice），模型可自由决定调不调；
  query 由模型构造（工具 schema），prompt 还要求改写重试 ≤2 次 ⇒ 工具路径属 L1+L2，是真 agentic。
- 佐证「整体不是」：主路径是 L0 预检索，且 prompt 规定 `<documents>` 优先 ⇒ 命中时模型无需调工具 ⇒ 多数请求实际停在 L0。

**本轮新发现（重要）：kbIds 作用域逃逸** —— 详见 `MEMORY.md` 的「隐患 a」。
- 链路：`chat.service.ts:87` 不传 kbIds → 工具 `kbIds` 只能模型填 → 模型不知道 → `undefined`
  → `rag.service.ts:176` `filter = undefined` → **检索全部知识库**。
- 这是**隔离性**问题（可能答出用户未勾选知识库的内容），不只是准确性问题。
- 已核实修法可行：`tool()` 的 func 类型是 `RunnableFunc<In,Out,ToolRunnableConfig>`，
  `RunnableConfig.configurable` 存在 ⇒ 可用 `configurable: { kbIds }` 传请求级作用域。
- 已核实 `content_and_artifact` / `responseFormat` 在 @langchain/core@1.2.3 存在。

教学点：**把控制流交给模型后，约束必须由 harness 强制**；模型既不知道 kbIds，也无法「选择」遵守。
